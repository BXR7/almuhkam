# Isolate Prisma data access and enforce revocable administrator authorization

The application trusted a published fallback JWT signing key and any valid token role, seeded a fixed administrator password, exposed drafts by slug, and had no versioned database security boundary. This change requires a new random signing secret, validates live eight-hour sessions and current permissions on every protected page/action, removes credential seeding, adds persistent login/contact quotas and input validation, and prevents draft disclosure and notification HTML injection.

A manual SQL migration moves all five existing tables to app_private without deleting records, creates private Session/RateLimit tables, separates NOLOGIN ownership from a narrowly granted runtime login, revokes API table/column grants, enables/forces RLS for the server role and sets fail-closed owner defaults. Prisma models map the private schema. Database SQL is never automatically applied by build/start/CI. Patched dependencies and response headers are included; the public page design is retained. The fixed public header no longer obstructs admin logout.

Validation: production build, lint, four unit scenarios, seven real Chromium scenarios, fresh PostgreSQL forward migration/read-only privilege assertions/rollback-transaction checks, original row-count/digest comparisons and an empty Prisma schema diff all passed. Production npm audit reports zero vulnerabilities. Full audit retains five high development-only package entries from the unpatched braces chain; no audit suppression or incompatible downgrade.

Production status: no production access or changes, credential rotation, merge or deployment. All six Supabase Advisor findings remain unverified; the remaining two are unknown. Hosted API/GraphQL grants, actual runtime identity, backup restorability, SMTP and external integrations require operator evidence. Schema relocation needs a coordinated maintenance window and invalidates legacy sessions. Read-only diagnostics, limitations, an approval-gated deployment/rollback runbook and CI tests are included in docs/security and security/.

Review blockers before production execution: verify a restorable backup and a production-representative isolated rehearsal, inspect every Advisor finding and effective privilege, approve role provisioning/coordinated secret/password rotation, validate pooler/TLS and API denial, and approve the explicit execution boundary. Do not merge/deploy automatically.
