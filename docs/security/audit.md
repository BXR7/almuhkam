# Aljlal security audit and architecture

Audit date: 2026-10-11. Repository baseline: `a9c82c8` (main). Target production project reported by operator: `aljalal-db`. No production connection, dashboard session, backup, Advisor export or deployment environment was available. No production SQL, credential rotation, record mutation, merge or deployment was performed.

## Complete repository flow

All database access is server-side Prisma. No Supabase client SDK, browser database key, REST/RPC client, custom route handler or other Server Action module was found. `src/lib/actions.js` is the exported action boundary; inline delete wrappers delegate to its guarded functions. Public database consumers are blog list, blog detail/metadata, portfolio and sitemap. Static home/services/about/contact pages do not access private records. Admin overview, blog/project edit/list/new, inquiries and settings have explicit checks before rendering or querying. Admin layout revalidates the session and avoids inquiry counts for editors. Login stays accessible to logged-out users; middleware is now the Next 16 `proxy.js` routing optimization, never the authorization authority.

No plaintext administrator password column was found: `User.password` stores bcrypt output when seeded/provisioned. This hash is highly sensitive. Customer inquiry fields include name, email, phone and free text; full inquiry objects are sent only to authorized administrator components. Server error messages no longer include action input/database exception details. Notification processing still sends customer information to configured SMTP recipients and must follow approved retention/privacy rules.

The original database identity is ONLY `DATABASE_URL`: no role, ownership, BYPASSRLS, pooler identity or production environment value can be inferred from source. PostgreSQL owners usually bypass RLS, superusers/BYPASSRLS always do, and ordinary roles require grants plus policies. See [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Runtime and migration identities must be tested separately using `security/diagnostics.sql`.

No tracked real connection URLs or private environment files were found in the current checkout. This does not establish that git history, deployment logs or external secret stores are clean. The published fallback/password are compromised by publication and must not be reused. README/deployment notes are not authoritative evidence of deployed configuration.

## Final architecture proposed by this PR

No application table needs direct Supabase Data API access. The repository uses Next server actions and Prisma only. After confirming other consumers, disable Data API (and verify GraphQL access independently). No application schema must be exposed. If shared-project integrations require an API, use a distinct empty/curated `api` schema with individually reviewed views/policies; never expose `app_private`. Supabase supports disabling unused Data API access: [Securing your API](https://supabase.com/docs/guides/api/securing-your-api).

Move User, Inquiry, Setting, Post and Project into `app_private` using ALTER TABLE SET SCHEMA, preserving table identity, indexes, data and relationships. Public content is delivered through publication-filtered server queries, while private records have role checks. Keeping all models private prevents an accidental browser key from acquiring content drafts, customer records or hashes. Add private Session and RateLimit tables. Prisma models explicitly map their schema using Prisma 6 multiSchema support; DATABASE_URL remains a server-only deployment secret.

`aljalal_owner` is a new NOLOGIN schema/table owner and future migration role; trusted operators SET ROLE to it for DDL. It is never a runtime identity. `aljalal_runtime` is a NOLOGIN permission group without elevated attributes. `aljalal_app` starts NOLOGIN and is enabled only by the operator after provisioning a secret password and testing the exact pooler connection. It inherits only the runtime group. Runtime gets schema USAGE, read-only User, content/inquiry/session/limiter CRUD, and settings read/insert/update. No table ownership, DDL, TRUNCATE, user credential writes, grant option, SUPERUSER or BYPASSRLS. Review global PUBLIC privileges and role inheritance before approving; the migration deliberately avoids broad changes to shared Supabase schemas.

All seven tables have ENABLE and FORCE RLS with a policy solely for the runtime group. This policy intentionally permits server-managed rows: custom JWT user IDs/roles are application identities, NOT auth.uid() or PostgreSQL roles. The database boundary isolates the trusted server from Data API roles, while application permission checks isolate editors from administrators. Migration/provisioning operations that need row access run through the separately authorized operator identity; FORCE RLS also constrains the NOLOGIN owner unless the operator explicitly manages policies.

Revoke existing table and column ACLs from nonowners before relocation. New schema has no PUBLIC USAGE or CREATE. New owner defaults grant neither table/sequence access nor function execution/type usage to PUBLIC; future objects receive no automatic runtime grants. Future changes must run as owner inside app_private with explicit grants and RLS policies, then run negative tests. Never create new app tables through postgres/public defaults. A forgotten policy/grant in the private schema fails closed. The runtime role is not an event-trigger/DDL operator; do not install broad project-wide DDL hooks during this remediation.

Session changes invalidate all legacy sessions. New session JWTs contain only sub/jti plus standard claims. Database rows expire after eight hours; logout revokes the row. Operator password/role incident procedure revokes all rows for the user in the same transaction as credential remediation. JWT rotation replaces the environment secret and invalidates all tokens without accepting an old compromised key. No automatic credential changes are included. Expired session/limiter cleanup is a separately approved operational retention job, not part of the migration.

Authorization must live in every server entry point, as recommended by [Next.js authentication guidance](https://nextjs.org/docs/app/guides/authentication). Cookie settings remain HttpOnly, SameSite=Lax, Secure in production. Next's built-in Server Action origin checks remain enabled; no permissive allowedOrigins override. Deployment must restrict trusted forwarded Host headers and configure ingress limits; runtime never trusts arbitrary X-Forwarded-For as an authentication signal.
