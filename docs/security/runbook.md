# Approval-gated production rollout and rollback

This PR does not authorize execution of the production procedure. No automatic migrations are wired to npm build/start or CI. Versioned SQL in `security/migrations` is applied manually through a reviewed operator session; Prisma schema tracks the resulting mappings. Do not run prisma db push, migrate reset, destructive diff-generated migrations or seed scripts against production. Existing production has no committed Prisma migration history; do not invent/baseline that history without schema introspection and a separate reviewed migration plan. `security/test-baseline.sql` is ONLY an isolated fixture matching the original repository, never a production migration.

See [PR #1 deployment and compatibility review](pr1-deployment-review.md) for the restricted-operator correction and unresolved provider/pooler assumptions. The migration grants its executing trusted operator owner membership; review that identity before execution. FORCE RLS still restricts non-BYPASS operators: ownership alone does not authorize provisioning or reading row digests.

## Evidence gate: read only

1. Confirm the target project ID/name is `aljalal-db` and obtain a scoped operator connection through the approved secret manager. Never paste its URL, JWT, account hashes or inquiry rows into PR/logs. Record who owns the approval and the incident window.
2. Run `security/diagnostics.sql` as the actual deployed Prisma login and separately as operator. Export all Advisor findings, including the two not provided in the request, and dashboard Data API, exposed schemas, GraphQL, backup/PITR and extensions settings. A NULL pgrst setting is inconclusive. Inventory external API consumers, views, triggers, RPC functions and any dependencies on the five public table names.
3. Audit public schema CREATE privileges and all role memberships. `aljalal_app` must not inherit migration/owner/API identities, DDL permissions, elevated role attributes or unrelated sensitive object access. Review grants outside the private app schema too. Confirm no app query needs Supabase auth.uid().
4. Inspect whether the published seed administrator exists using identity-only queries; verify compromised-password status only inside an approved secured tool that outputs a boolean. Do not export the stored hash. Prepare coordinated replacement credentials and revoke sessions in the same transaction; this PR never overwrites existing credentials.

## Backup and isolated rehearsal gate

1. Verify a recent full restorable Supabase backup/PITR point with timestamp, retention and recovery owner. Actually restore it to a separate protected project; a green backup status is not a restore test. Store logical backups encrypted/access controlled if used; Supabase physical backup/role support must be verified for this project.
2. Compare the restored schema/roles/extensions/triggers/grants to diagnostics. Rehearse the exact SQL with production-representative privileges and dependencies, not only the minimal local fixture. Any unexpected existing app_private schema/aljalal role/policy causes the migration to abort for review. Do not edit away that guard on production.
3. Record per-table counts and deterministic record digests at a consistent snapshot while writes are stopped. Include User/Post/Project/Inquiry/Setting; capture FK/index definitions. Digest full rows only inside trusted DB; store counts and aggregate hashes, never customer rows. For very large tables stream ordered data to a protected digest process rather than materializing a giant aggregate string.
4. Rehearse rollback, compare the same counts/digests, and test the exact Supabase pooler identity/TLS parameters with the prepared runtime role. Validate REST and GraphQL negative probes with anon and authenticated keys; these must return denied/missing resources without private fields. Review service_role privileges separately because BYPASSRLS does not bypass GRANT/schema USAGE.
5. Build and test the candidate with new secrets in isolated deployment. Validate original page design, published content, intended isFeatured filtering, forms, admin/editor CRUD, private route/action denial, current-role changes, session expiry/revocation, origin rejection, ingress quotas and actual SMTP delivery. Never reuse production customer data in a public preview.
6. Prepare a compatibility rollback build from this fixed code: original five models map to public; Session/RateLimit stay app_private; protected authentication remains. Validate it against rollback schema. Do not roll back to the baseline with the published key/password. Record artifact/version identifiers and protected environment snapshots.

**STOP for explicit production approval here.** Present backup restore evidence, diagnostics, final migration diff, role provision/credential rotation details, both tested builds, count/digest results, rollback rehearsal and expected outage. Without these, production execution is prohibited even if the PR merges later.

## Approved execution only

1. Schedule a maintenance window; this schema relocation is not a rolling zero-downtime migration. Pause new inquiries/content changes, drain old application instances and prevent automatic deployment jobs. Lock timeout is five seconds; table moves acquire strong locks. If blocked, the transaction fails—investigate, do not raise timeouts blindly.
2. Capture final consistent counts/digests and backup/PITR point. Execute `security/migrations/001_private_schema.sql` with ON_ERROR_STOP enabled from an authorized operator, in its existing single transaction. If any step fails, verify rollback before proceeding. No records are deleted by this migration.
3. Provision a new unique random database password into the secret manager and set it securely (e.g. interactive psql `\password aljalal_app`, without SQL history/logged password literals). Then enable LOGIN on aljalal_app. Use provider-supported TLS (`sslmode=verify-full` with a trusted CA when supported); verify the actual direct/pooler username/project suffix resolves to that role. Do not replace the old production credential without the coordinated plan; retain old credential sealed only for the approved compatibility fallback, then retire it separately.
4. Verify runtime has only required grants and no ownership/BYPASSRLS. Rotate JWT_SECRET to a new cryptographically random value (e.g. openssl rand -base64 48 delivered directly to secret manager). New code rejects the historical fallback and invalidates all old sessions. Coordinate administrator re-login and any compromised-password remediation. Existing bcrypt hashes are preserved until explicit coordinated change.
5. Deploy the already reviewed fixed build manually with DATABASE_URL pointing to the new runtime login, JWT_SECRET and approved SMTP/site URL configuration. No owner/admin DB secret in the application or NEXT_PUBLIC variables. Do not run seed/provision as part of deploy. Private schema must never be an exposed Data API schema. Disable unused Data API after verifying external consumers; independently test GraphQL/RPC endpoints and invalidate schema caches through supported Supabase operations.
6. Before reopening traffic compare counts/digests/indexes/FKs, rerun diagnostics, `security/verify.sql` and full Advisor, validate public retrieval/draft denial, submit an explicitly authorized canary inquiry, admin login/dashboard, editor content access/private denial, session revocation, CRUD on approved synthetic canary content, SMTP and API negative probes. Canary deletion is a separate explicit production-record mutation approval; do not silently clean it up.
7. Reopen traffic, monitor permission errors, login/inquiry success rates, 5xx, pooler behavior and security events without logging input/tokens. Export before/after evidence with timestamps. Mark only individually verified Advisor findings resolved; track any remaining extension/function issues separately.

## Rollback (separate execution approval)

Pause writes and drain instances. Determine whether failure occurred before transaction commit (no schema rollback needed) or after commit. Preserve current data; never restore a stale backup over newly accepted records. Review record counts/digests and logs. Execute `security/rollback/001_private_schema.sql` only after confirming public has no conflicting table names. It moves the five original tables back, retains all records plus new session/limiter tables, keeps restrictive grants/FORCE RLS/policies and retains the private owner/runtime roles. It deliberately does not restore insecure API privileges, published credentials or PUBLIC function defaults. Use the tested compatibility fixed build and existing runtime login. Revalidate counts/digests, admin/editor behavior and API denial before reopening. If the rollback transaction fails, it aborts; escalate to recovery owner and use the verified restore only as an explicitly approved last resort with post-backup-write reconciliation.

Password/JWT changes cannot be meaningfully undone by SQL rollback. Never re-enable a compromised key/password; users must log in again. Keep Data API disabled/private schema unexposed throughout. A backup restore is for disaster recovery, not an automatic privilege rollback.

## Ongoing security defaults

Future migrations use SET ROLE aljalal_owner; only app_private CREATE is intended. Add policies/grants explicitly; run negative privilege/API tests with every migration. Keep application/owner credentials separate, rotate through the secret manager and revoke affected Session rows transactionally during password/security changes. Set ingress per-source and global limits for login/contact Server Actions before rollout; account/email quotas alone do not stop distributed abuse. Approve a bounded cleanup/retention job for expired Session/RateLimit rows separately (no cleanup deletion is authorized here). Patch production dependencies continuously; track the development-only braces advisory without downgrading Next tooling or suppressing audit output.
