## Confirmed migration bug and correction

The original migration failed on isolated PostgreSQL 17 as a database-owning `CREATEROLE`, `NOSUPERUSER`, `NOBYPASSRLS` operator with SQLSTATE `42501`: `must be able to SET ROLE "aljalal_owner"`. Earlier regression tests migrated as superuser and missed this failure. Supabase's postgres identity is not a PostgreSQL superuser. PostgreSQL 16+ role creator membership does not automatically supply SET/INHERIT rights.

The migration now explicitly grants only the trusted executing operator membership in the new owner role. PostgreSQL 16+ gets explicit SET and INHERIT options; PostgreSQL 15 uses its supported membership syntax. Runtime and API roles receive no owner membership. The regression harness creates the original tables and applies the migration using a restricted operator, checks runtime owner membership is absent, and rehearses rollback under that operator as well as checking row digests and API denial. Both PostgreSQL 15 and 17 passed locally. This proves vanilla PostgreSQL behavior, not Supabase provider-hook compatibility. [Supabase role restrictions](https://supabase.com/docs/guides/database/postgres/roles-superuser), [PostgreSQL membership](https://www.postgresql.org/docs/17/role-membership.html).

## Live Supabase assumptions that remain rollout blockers

- Obtain actual PostgreSQL version, deployed login and effective privileges using diagnostics. Verify the operator can create roles, grant membership with required options, own/move each original table and revoke every existing ACL. Supabase provider restrictions may exceed vanilla PostgreSQL. The SQL intentionally aborts on role/schema/policy drift and inherited runtime public CREATE; do not bypass those guards.
- Membership in the owner role is a durable privileged grant to the executing operator. Review that identity explicitly; never execute as a shared application/API role. Owner default privileges protect objects created **as owner**, not objects accidentally created as postgres or another operator. Future DDL must use SET ROLE aljalal_owner and explicit reviewed grants/policies.
- FORCE RLS also restricts a non-BYPASS owner/operator. Merely owning the schema does not authorize row reads or administrator provisioning. Existing hashes/accounts are preserved. `provision-admin` is not verified with the restricted operator and must not be run in production until a separately reviewed, narrowly authorized provisioning policy/identity is rehearsed. Count/digest evidence needs an authorized read identity; never disable RLS to collect it. The local harness uses its synthetic superuser for independent digest verification only.

Test anon, authenticated and service_role negative probes independently; BYPASSRLS alone does not confer schema/table grants. Rehearse prepared statements, interactive transactions, login/session checks, rate-limit upserts and concurrent inquiries over the actual pooler, not just local direct PostgreSQL.

## Confirmed Preview failure and fix

Loading next.config.mjs does not sign or verify tokens and should not require an authentication key. Removing its signingKey import/call permits builds without embedding, generating or substituting a key. signSession still throws for invalid configuration; verifySession returns null. The shared signingKey function also protects rate-limit HMAC generation. Missing configuration therefore denies login, private access and inquiry submission; it never issues an insecure session. Existing-session verification rechecks the runtime key on every call. No build-only fallback, environment exemption or Vercel-specific bypass exists. Obvious whitespace/repeating secrets are now rejected in addition to short keys and the published historical key; syntactic checks cannot prove randomness, so secure independent generation remains required.

CI deliberately builds without JWT_SECRET and then runs authenticated browser tests with a generated synthetic key. Unit tests exercise production-mode invalid-key issuance/verification and configuration loading. A second local production server starts without the key: public retrieval works against the synthetic DB, but an otherwise valid existing session and correct-password login are denied without creating a session/cookie. Build success is not runtime readiness.

See [Preview configuration](preview-configuration.md) for exact variable names, isolated-database requirements and operator steps. Production still has public tables and is incompatible with this PR's app_private mappings. Do not merge, promote or deploy this PR to Production before the separately approved runbook cutover.
